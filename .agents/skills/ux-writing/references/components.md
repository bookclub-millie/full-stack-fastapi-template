# 컴포넌트별 문구

제목·설명·버튼을 한 묶음으로 쓴다. 같은 말을 세 번 반복하지 않는다.
길이를 줄이려고 조건·대상·불이익을 생략하거나, 문구 작업으로 UI 구조를 바꾸지 않는다.

| 컴포넌트 | 작성 기준 | 예시 |
|---|---|---|
| 환영 화면 제목 | 사람에게 먼저 인사한다. 기능명을 그대로 쓸 의무는 없다. | `다시 만나 반가워요` |
| 설명 | 제목에 없는 도움·이유·다음 결과를 대화하듯 전한다. | `계정을 만들고 함께 시작해요.` |
| 버튼 | 실제 행동·받는 결과를 명확히 쓴다. 친근함 때문에 모호하게 만들지 않는다. | `로그인`, `계정 만들기`, `이메일로 링크 받기` |
| 입력 라벨 | 입력 대상을 짧고 분명하게 쓴다. | `이메일`, `비밀번호` |
| 플레이스홀더 | 형식 예시나 꼭 필요한 힌트를 쓴다. 라벨을 대체하지 않는다. | `name@example.com` |
| 도움말·입력 오류 | 실제 조건 또는 고치는 방법을 편하게 말한다. | `비밀번호가 서로 달라요. 다시 확인해 주세요.` |
| 다이얼로그 | 제목은 구체적인 질문, 본문은 영향, 버튼은 실제 선택을 담는다. | `항목을 삭제할까요?` / `삭제`, `취소` |
| 토스트 | 실제 결과를 짧게 전한다. 중요한 복구 안내를 토스트에만 맡기지 않는다. | `비밀번호를 바꿨어요.` |
| 빈 화면 | 정상적인 빈 상태와 가능한 첫 행동을 연결한다. | `아직 만든 항목이 없어요. 첫 항목을 만들어 볼까요?` |
| 탐색 제목·메뉴·탭 | 위치와 대상을 쉽게 찾도록 명칭을 일관되게 쓴다. 환영 제목과 구분한다. | `설정`, `프로필` |
| 툴팁·팝오버 | 대상과 관련된 필요한 정보만 담는다. 접근 가능한 이름을 대신하지 않는다. | 실제 기능에 맞게 작성 |

## 친근한 제목, 명확한 동작

- 화면 제목이 `다시 만나 반가워요`여도 버튼·문서 제목·탐색 링크의 `로그인`은 유지할 수 있다. 역할이 다르므로 불일치가 아니다.
- `가보자고!`, `출발!`, `좋아요!`는 어떤 동작인지 숨기는 버튼이면 쓰지 않는다.
- `이메일로 링크 받기`는 실제로 복구 링크를 이메일로 보내는 흐름에서 쓴다. 비밀번호를 직접 바꾸는 버튼은 `비밀번호 바꾸기`다.
- 안내를 닫기만 하는 버튼은 `확인`이어도 된다. 삭제나 구매를 `확인`으로 숨기지 않는다.
- `다시 시도`, `실행 취소`, `문의하기`는 해당 동작과 경로가 있을 때만 쓴다.

## 입력·보안

비밀번호 길이·허용 문자·필수 여부는 실제 검증 조건을 따른다.
서버가 원인을 구분하지 않는 인증 실패는 특정 계정의 존재나 비밀번호 오류로 단정하지 않는다.
복구 요청의 일반 성공 응답도 실제 이메일 도착이나 계정 존재를 보장하지 않는다.
